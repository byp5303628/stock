# 财报指标存储 — 方案设计

## 1. 背景与目标

### 1.1 业务背景

在建设完整的股票分析体系过程中，财报数据是基本面分析的核心输入。当前系统已有日K线数据（前复权/后复权）和交易策略回测能力，但缺乏对上市公司财务报表数据的结构化存储和管理能力。

现金流量表、资产负债表、利润表这三张核心财务报表的指标数据，目前没有统一的存储模型。分析场景（如策略回测中的基本面过滤、指标计算）无法直接获取和使用财报数据。

### 1.2 目标

- 对三张核心财务报表（现金流量表、资产负债表、利润表）的指标进行格式化存储
- 基于已有的元数据系统（feature-03/04）定义财报数据模型，支持模型持续扩展
- 确保每条数据仅存储一次，通过股票代码+报表类型+报告日期去重
- 接入外部数据源获取财报数据，完成字段映射与写入
- 提供标准 REST API 供查询和数据摄取

### 1.3 非目标（明确不做什么）

- 前端可视化展示页面（后续 feature 单独建设）
- 财务比率计算与指标分析（如ROE、资产负债率等）
- 财报数据的自动定时同步（需 schedule task 系统配合）
- 历史财报数据的批量补录与迁移
- 除三大报表外的其他财务数据（附注、审计意见等）
- 财务数据变更追踪（修正/重述版本的追溯）

### 1.4 关键指标

| 指标 | 目标值 |
|------|--------|
| 单条财报数据写入 | < 500ms |
| 按股票代码按年份范围查询 | < 200ms |
| 数据去重准确率 | 100%（唯一约束保障） |
| 新增指标字段的扩展成本 | 无需修改 Java 代码 |

## 2. 方案设计

### 2.1 领域模型

```
FinancialReport（财务报告）
├── id: Long
├── code: String              // 股票代码，如 "000001"
├── reportType: String        // 报表类型：CASH_FLOW / BALANCE / INCOME
├── reportDate: String        // 报告截止日期，如 "2024-12-31"
├── reportPeriod: String      // 报告期：Q1 / Q2 / Q3 / Q4 / YEARLY
├── reportData: Map<String, Object>  // 指标数据（key=元数据字段名, value=指标值）
├── gmtCreate: Date
└── gmtModified: Date
```

**实体关系：**

```
StockInfo (股票信息)
    │ 1
    │
    └── * FinancialReport（按 code 关联）

MetadataModel (元数据模型)
    ├── code = "cash_flow_statement"  ← 定义现金流量表的字段结构
    ├── code = "balance_sheet"        ← 定义资产负债表的字段结构
    └── code = "income_statement"     ← 定义利润表的字段结构

FinancialReport.reportData 中的 key 与元数据模型的字段名（fieldName）一一对应。
```

**设计决策：** 使用 JSON 列存储指标数据，而非为每个报表类型创建单独的宽表。原因：

1. **可扩展性**：新增指标字段只需在元数据系统中添加字段定义，无需 DDL 变更
2. **与现有模式一致**：`stock_statistics.statistics`、`stock_info.ext_info`、`trade_policy_regression.detail` 均已采用 JSON 列
3. **业务隔离**：每种报表类型有自己的元数据模型定义，JSON 结构由元数据 schema 约束
4. **查询可行性**：MySQL JSON 列支持 `JSON_EXTRACT`、`->>` 等函数，可满足基本查询需求

### 2.2 数据模型（含 DDL）

#### 新建表：financial_report

```sql
create table if not exists financial_report
(
    id            bigint                 not null primary key auto_increment,
    code          varchar(16)            not null comment '股票代码',
    report_type   varchar(16)            not null comment '报表类型：CASH_FLOW / BALANCE / INCOME',
    report_date   varchar(32)            not null comment '报告截止日期，如 2024-12-31',
    report_period varchar(16)            not null default '' comment '报告期：Q1/Q2/Q3/Q4/YEARLY',
    report_data   json                            comment '指标数据（JSON），key 为元数据字段名',
    fiscal_year   int                             comment '会计年度，如 2024',
    currency      varchar(8)             not null default 'CNY' comment '货币单位',
    unit          varchar(8)             not null default '元' comment '计量单位：元/万元/亿元',
    source        varchar(32)            not null default '' comment '数据来源',
    gmt_create    datetime               not null default now(),
    gmt_modified  datetime               not null default now() on update now(),
    unique index uniq_idx_code_type_date (code, report_type, report_date),
    index idx_code (code),
    index idx_report_type (report_type),
    index idx_report_date (report_date),
    index idx_fiscal_year (fiscal_year),
    index idx_gmt_modified (gmt_modified)
) engine = InnoDB default charset = utf8mb4 comment '财务报告数据表';
```

**索引说明：**
- `uniq_idx_code_type_date` — 唯一约束实现去重：(code, report_type, report_date) 唯一，同一只股票同一张报表同一季度仅一条记录
- `idx_code` — 按股票代码查询
- `idx_report_type` — 按报表类型过滤
- `idx_report_date` — 按日期范围查询
- `idx_fiscal_year` — 按会计年度查询

**去重策略：** INSERT ... ON DUPLICATE KEY UPDATE 覆盖更新（后写入覆盖前一次），确保幂等性。

### 2.3 状态模型

FinancialReport 无复杂状态流转，核心状态是数据的存在性：

```
不存在 → INSERT → 已存在
已存在 → ON DUPLICATE KEY UPDATE → 已覆盖
```

数据获取任务可使用现有的 Task 系统（`Task` / `TaskHandler`），支持 INIT → PROCESSING → SUCCESS/FAIL 状态流转。

#### 执行路径

**写入流程（外部数据 → 存储）：**

```
FinancialDataRemoteClient.fetchReport(code, reportType)
    → 解析外部 API 返回的 JSON
    → field mapping（外部字段名 → 元数据字段名）
    → FinancialReportDomainService.save(report)
        → 唯一键冲突时执行 ON DUPLICATE KEY UPDATE
```

**查询流程（API 请求 → 响应）：**

```
GET /api/financial-reports?code=000001&reportType=BALANCE
    → FinancialReportDomainService.query(code, reportType, dateRange)
        → FinancialReportMapper.selectByCodeAndType(...)
    → 返回 FinancialReportDTO 列表
```

**不采用 Process Engine 的原因：**
财报存储本质是 CRUD + 外部数据同步，没有复杂的多步骤业务流程。直接使用 Controller → Service → Mapper 的模式更简洁，与 MetadataController 的设计一致。

#### 外部数据源集成

在 `stock-remote` 中新增 `FinancialDataRemoteClient`，模式与 `HistoryStockClient` 一致：

- 使用 `Unirest` HTTP 客户端（项目已有）
- 封装对公开数据源的 HTTP 调用
- 解析 JSON 响应并映射为内部模型
- 支持按股票代码 + 报表类型查询

**数据源说明：**
当前系统的 K 线数据源为 `web.ifzq.gtimg.cn`（腾讯股票接口）。财报数据计划使用同源接口或备选的东方财富/Akshare 等公开数据源。具体 endpoint 在实现阶段确认，本设计确保接入层与业务层解耦——即使更换数据源，也只需修改 `FinancialDataRemoteClient` 一个类。

### 2.6 关键逻辑

#### 去重与幂等写入

```java
// FinancialReportDomainService.save()
public Result<FinancialReport> save(FinancialReport report) {
    // 1. 唯一键检查：code + reportType + reportDate
    // 2. ON DUPLICATE KEY UPDATE 实现幂等
    FinancialReportDO doEntity = DbConverter.toDbEntity(report);
    financialReportMapper.upsert(doEntity);
    // 3. 返回完整记录
    return Result.ok(DomainConverter.toDomain(financialReportMapper.selectById(doEntity.getId())));
}
```

MyBatis Mapper 中使用 `INSERT ... ON DUPLICATE KEY UPDATE`：

```xml
<insert id="upsert" parameterType="FinancialReportDO">
    INSERT INTO financial_report (code, report_type, report_date, report_period,
        report_data, fiscal_year, currency, unit, source, gmt_create, gmt_modified)
    VALUES (#{code}, #{reportType}, #{reportDate}, #{reportPeriod},
        #{reportData}, #{fiscalYear}, #{currency}, #{unit}, #{source}, now(), now())
    ON DUPLICATE KEY UPDATE
        report_data = VALUES(report_data),
        report_period = VALUES(report_period),
        report_data = VALUES(report_data),
        fiscal_year = VALUES(fiscal_year),
        currency = VALUES(currency),
        unit = VALUES(unit),
        gmt_modified = now()
</insert>
```

#### 外部数据字段映射

外部数据源返回的字段名与内部元数据字段名可能不一致，需要做映射转换：

```java
// 字段映射配置（可在配置文件中管理）
Map<String, String> fieldMapping = new HashMap<>();
// 东方财富字段 → 内部字段
fieldMapping.put("totalAssets", "total_assets");
fieldMapping.put("currentAssets", "current_assets");
fieldMapping.put("totalLiabilities", "total_liabilities");
fieldMapping.put("totalEquity", "total_equity");
// ...

// 转换逻辑
Map<String, Object> mappedData = new HashMap<>();
for (Map.Entry<String, Object> entry : rawData.entrySet()) {
    String internalField = fieldMapping.getOrDefault(entry.getKey(), entry.getKey());
    mappedData.put(internalField, entry.getValue());
}
report.setReportData(mappedData);
```

#### 分页查询

实现通用的分页查询模式，与项目中的 ResponseDTO 一致：

```java
public PageResult<FinancialReport> query(String code, String reportType,
        String startDate, String endDate, Integer fiscalYear, int page, int size) {
    int offset = (page - 1) * size;
    List<FinancialReportDO> list = financialReportMapper.selectPage(code, reportType,
            startDate, endDate, fiscalYear, offset, size);
    long total = financialReportMapper.count(code, reportType, startDate, endDate, fiscalYear);
    return new PageResult<>(list.stream().map(DomainConverter::toDomain).collect(toList()), total, page, size);
}
```

## 3. 备选方案

### 方案 A：每种报表类型一张独立宽表

为现金流量表、资产负债表、利润表各建一张独立宽表，每个指标对应一个独立列。

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A：独立宽表** | 查询直观、SQL 简单、强类型约束 | 新增指标需 DDL 变更，不满足可扩展性要求 |
| **B：单表 JSON（选中方案）** | 可扩展、与元数据系统联动、无 DDL 变更 | JSON 字段查询需要 MySQL JSON 函数 |
| **C：EAV 模式** | 最灵活，行级存储 | 查询性能差，需要大量行转列操作，复杂度过高 |

**未选择 A 的原因：** 需求明确要求"未来需要新增报表类型或指标字段，则通过扩展元数据模型实现，无需修改存储层代码"。独立宽表无法满足此要求。

**未选择 C 的原因：** EAV 模式虽然理论上最灵活，但查询时需要复杂的行转列（PIVOT）操作，性能差且 MySQL 没有内置 PIVOT 功能。JSON 列在灵活性和查询性能之间取了平衡。

### 方案 B2：使用元数据系统直接存储数据

一部分方案建议通过元数据系统的 ext_info 或 JSON Schema 来直接托管数据。否决理由：元数据系统是 metadata（关于数据的数据），不是数据存储层。数据与元数据应分离存储。

## 7. 未解决问题

| 问题 | 说明 | 建议方案 |
|------|------|---------|
| 外部数据源具体 endpoint 和 API 认证 | 需调研腾讯/东方财富的财报接口可用性和频率限制 | 实现阶段确认，预留接口适配层 |
| 财报数据的历史覆盖范围 | 是否从上市之日起全量拉取？ | 首批仅拉最近 2-4 年，后续通过定时任务增量更新 |
| 多货币/多单位的统一处理 | 不同市场（A股/港股）的单位可能不同 | `currency` 和 `unit` 字段存元数据，展示时由前端处理 |
| 同一季度多次修正（restatement） | 公司可能会修正已发布的财报 | 当前覆盖更新（取最新），后续可考虑版本号方案 |
| 是否需要缓存 | 财报数据变更频率低，适合缓存 | 待第一阶段上线后根据性能评估是否需要引入缓存 |
